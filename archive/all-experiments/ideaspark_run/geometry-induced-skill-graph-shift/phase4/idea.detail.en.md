# GISS-2x2: Matched-State Geometry-Action Compatibility for Frozen Robot Policies

**Method.** Matched-State Geometry-Action Crossover (GISS-2x2)

## Motivation
**Problem framing.** A frozen robot policy can appear robust across geometric variations for several incompatible reasons: it may use visible functional geometry to select the current action, exploit an open-loop default that happens to work, or recover later through closed-loop feedback. Aggregate success cannot separate these explanations because geometry changes usually also change the realized state trajectory, contact dynamics, and inference history. The structural bottleneck is therefore an identification problem: measuring geometry-conditioned action compatibility while holding the decision state fixed and allowing the same native downstream success criterion for every comparison.

This issue is concrete in scalable manipulation suites such as RoboTwin 2.0 (dblp:journals/corr/abs-2506-18088) and in systematic geometry generalization benchmarks such as GemBench (openalex:W4403116255). Their task diversity makes the phenomenon observable, but their ordinary rollout comparisons do not provide the counterfactual cells needed to ask whether the action chunk elicited by geometry A is specifically better in A than the chunk elicited by endpoint-equivalent geometry B, and symmetrically for B. GISS-2x2 turns that missing comparison into a narrow matched-state diagnostic for frozen policies.

**Why now.** The gap is now practical to close because recent simulators expose broad, editable functional geometry and reproducible task families—RoboTwin 2.0 (dblp:journals/corr/abs-2506-18088)—while GemBench (openalex:W4403116255) and Any3D-VLA (openalex:W7127541930) make 3D generalization a current evaluation target rather than an incidental stress test. At the same time, local open frozen policies such as OpenPI pi0.5 and CLOVER can be queried repeatedly without training or paid APIs. State serialization, collision-mesh editing, and deterministic inference controls therefore make a four-cell checkpoint crossover possible at a scale that remains small enough for manual pair validation.

**Why prior work stopped.**
- `dblp:journals/corr/abs-2506-18088` (arXiv 2025): RoboTwin 2.0 (dblp:journals/corr/abs-2506-18088) provides scalable robot data and task variations for evaluating manipulation policies.
  - _Did not do_: It did not restore one decision checkpoint across an endpoint-equivalent functional geometry pair and cross the two resulting action chunks through both recipient geometries.
  - _Structural reason_: Its unit of analysis is dataset or rollout performance, so the benchmark lacks a within-state counterfactual estimator for current action compatibility.
- `openalex:W4403116255` (arXiv 2025-05): GemBench (openalex:W4403116255) systematizes 3D manipulation generalization across controlled geometric variations.
  - _Did not do_: It did not query two source-geometry chunks from an identical checkpoint and execute both chunks in each recipient geometry under one terminal predicate.
  - _Structural reason_: Its split-based evaluation changes the condition being solved rather than constructing the crossed counterfactual cells needed to cancel recipient difficulty.
- `openalex:W4405956290` (arXiv (Cornell University) 2024): CoA-VLA (openalex:W4405956290) conditions robot action generation on an explicit chain of action-relevant affordance structure.
  - _Did not do_: It did not test whether an unmodified frozen policy's current native action chunk is selectively compatible with the functional geometry that elicited it.
  - _Structural reason_: Its mechanism places a structured affordance scaffold inside the policy, whereas the missing measurement requires geometry to be the only source-side intervention.
- `openalex:W7127541930` (arXiv (Cornell University) 2026): Any3D-VLA (openalex:W7127541930) targets stronger use of 3D scene information for vision-language-action behavior.
  - _Did not do_: It did not isolate a same-state own-versus-cross action advantage under paired functional geometries and native task success.
  - _Structural reason_: Representation and end-to-end policy evaluation do not by themselves supply the matched checkpoint, action swap, and recipient-controlled contrast required for identification.
- `openalex:W4403808753` (arXiv (Cornell University) 2024): CLOVER (openalex:W4403808753) detects visual prediction error and replans online to improve manipulation robustness.
  - _Did not do_: It did not compare own and crossed first action chunks from a byte-matched pre-action state before restarting each recipient rollout from the actual post-chunk observation.
  - _Structural reason_: Reactive recovery entangles error detection, replanning, and downstream feedback, so it cannot identify compatibility of the current action at the original decision point.

**What changes when the gap closes.** Closing the gap yields a policy-agnostic assay that can distinguish geometry-conditioned current actions from open-loop defaults and later recovery, localized to eligible task families rather than averaged into one capability score. It can complement the generalization claims studied by GemBench (openalex:W4403116255), Any3D-VLA (openalex:W7127541930), and the recovery behavior studied by CLOVER (openalex:W4403808753) by identifying exactly where native success depends on a geometry-compatible first chunk.

## Method
**Pipeline.** GISS-2x2 first compiles endpoint-equivalent functional geometry pairs and a corresponding appearance-only control while freezing the instruction, terminal predicate, and all non-geometry state. At a validated decision checkpoint, it queries one action chunk per source geometry from the same fresh inference template, then restores the checkpoint to execute both chunks in both recipient geometries. Native closed-loop success produces a matched-state interaction, and determinism, appearance, and state-jitter gates determine whether that interaction can be attributed to functional geometry compatibility within the registered scope.

### M0_background
*Set the preregistered scope, build controlled geometry instruments, and establish a restore-tested matched decision state before running the crossover.*

1. **Register eligible task families** (`S1`)
   - Before producing any crossover outcome, create a versioned UTF-8 JSON registration manifest. Its header stores the frozen-policy checkpoint digest, simulator build, task-family whitelist, and immutable registration time; each decision-event record stores $event_{id}, task_{family},$ instruction and terminal-predicate digests, an executable event detector, the admissible pre-action phase, deterministic pair-exclusion reason codes, the action-chunk horizon in controller ticks, baseline-trial numerator and denominator, the minimum accepted support, and endpoint-equal baseline-stratum boundaries. The exact values and executable definitions are not supplied. 【author decision: preregister the eligible task families, terminal and event rules, exclusions, action horizon, baseline-support threshold, and stratum boundaries before generating outcomes.】 Require the event detector to emit at most one tuple containing $event_{id},$ episode seed, simulator tick, and checkpoint request per episode; validate the manifest against a JSON Schema and freeze its cryptographic digest. Output the manifest, schema, and a machine-readable decision-event grammar that maps every accepted or rejected event to one reason code.
   - _Why:_ The claim is intentionally instrument-scoped; a fixed eligibility rule prevents a tiny diagnostic from expanding into a broad VLA competence claim.
2. **Compile geometry-pair instruments** (`S2`)
   - Compile one immutable pair record per registered task and endpoint-equivalence stratum. Each record contains $pair_{id}, task_{family},$ A/B asset identifiers, render-material descriptors, collision-mesh digests, mass, inertia, friction, joint and actuator parameters, instruction and object-identity digests, initial-state digest, terminal-predicate digest, and an $equivalence_{certificate}$ listing every compared endpoint field and tolerance. Functional records must differ in the registered collision-geometry field; appearance-control records must have identical collision and physics digests and differ only in declared visual fields. The admissible geometry transforms and endpoint acceptance test are not defined. 【author decision: specify for each task family the allowed functional transforms, endpoint fields and tolerances, and contact or dynamics changes that invalidate a pair.】 Run a schema validator that rejects undeclared differences, duplicate pair members, invalid initial configurations, or a failed equivalence certificate, and retain a field-level comparison report with each accepted pair manifest.
   - _Why:_ Functional pairs instantiate the source intervention, while appearance-only pairs provide a non-tautological control for rendering sensitivity.
3. **Capture a matched decision checkpoint** (`S3`)
   - At the registered event, serialize checkpoint z into a typed snapshot containing robot joint positions and velocities, object poses and velocities, controller integrators, task-automaton state, simulator clock and integrator state, sensor state, and all random-number-generator states; store geometry handles separately so A or B can be selected at restore. Canonically serialize every non-geometry field and require byte equality of its digest across the two recipients, together with equality of the instruction and terminal-predicate digests. Restore z independently under A and B, immediately reserialize it, and require the same non-geometry digest; any mismatch produces a field path, expected value, observed value, and S1 exclusion code rather than a usable checkpoint. Store $checkpoint_{uri},$ snapshot format version, cryptographic digest, $pair_{id}, event_{id},$ recipient-geometry injection key, and the complete invariant audit in the output index.
   - _Why:_ Fixing the decision state blocks open-loop state or dynamics mismatch from being counted as geometry-conditioned action compatibility.

### M1_matched_state_crossover
*Query geometry-conditioned chunks from one checkpoint, execute all four source-recipient cells, and estimate the recipient-controlled compatibility interaction.*

4. **Query source-conditioned chunks** (`S4`)
   - For each source $s\in {A,B},$ restore z, select $G_{s},$ and construct the same fresh history template $h_{0}$ from the registered instruction, current recipient-independent proprioception, current rendered observation, and explicitly empty prior-observation, prior-action, recurrent-state, and key-value-cache fields. Instantiate the frozen policy in evaluation mode from the same checkpoint, apply the same preprocessing and decode seed $\xi ,$ and emit $u_{s}$ as a typed native-action array with shape, control mode, coordinate frame, units, controller rate, valid-step mask, and digest. The controlled decoder and determinism test are not executable as written. 【author decision: preregister the policy-specific sampler or decoder, repeat count, shared-seed rule, distance d over equal-shaped action arrays, per-dimension normalization, and $\epsilon _{det}.$】 Repeat each identical render under exactly that query configuration, compute every pairwise scalar distance, and accept the source only when their maximum is at most $\epsilon _{det}.$ Save all query configurations, seeds, chunk digests, and distances in the audit, then destroy the policy instance and all recurrent, token, and key-value cache objects before the next query.

*Query the frozen policy at the same checkpoint z with a shared fresh history template $h_{0}$ and decode seed $\xi $; only the rendered source geometry $G_{s}$ changes.*
$$ u_s = \pi_\theta\!\left(o(z,G_s),h_0;\xi\right),\qquad s\in\{A,B\} \tag{1} $$


*An identical-render repeat must keep chunk variation below the preregistered determinism tolerance before the pair is eligible.*
$$ \max_{k,k'} d\!\left(u_s^{(k)},u_s^{(k')}\right) \le \varepsilon_{\mathrm{det}} \tag{2} $$

   - _Why:_ Only the visible source geometry may produce the chunk; shared history and repeatability checks prevent cache or sampling state from becoming the effective intervention.
5. **Execute the four crossover cells** (`S5`)
   - Materialize exactly four cell records indexed by $pair_{id}, policy_{id}, reset_{seed},$ recipient $r\in {A,B},$ and source $s\in {A,B}.$ For each cell, restore the identical checkpoint and random-number-generator states, select $G_{r},$ and send every valid command in $u_{s}$ unchanged through the policy's native controller at the registered rate and action-chunk horizon; apply no geometry-specific remapping beyond the controller's normal semantics, and stop early only when the registered native terminal predicate fires. Create a new frozen-policy instance after the injected chunk and seed it solely from the actual recipient rollout, never from the source query. The required history construction for stateful policies remains undefined. 【author decision: define per policy which actual recipient observations and executed actions fill every continuation-history slot, how missing slots are padded, and which recurrent or cached fields are reset.】 Continue from the actual post-chunk observation until native success, native failure, or the registered episode limit. Emit $Y_{r\leftarrow s}$ and a trace record containing all identifiers, checkpoint and chunk digests, pre- and post-chunk observation digests, executed actions, terminal reason and tick, binary success, and a cache-clean assertion.

*Cell $Y_{r\leftarrow s}$ is native task success when chunk $u_{s}$ is executed in recipient geometry r and the frozen policy then resumes from the actual post-chunk observation.*
$$ Y_{r\leftarrow s}=\mathbf{1}\!\left\{\mathcal{R}\!\left(z,G_r,u_s,\pi_\theta^{\mathrm{fresh}}\right)\models\tau\right\},\qquad r,s\in\{A,B\} \tag{3} $$

   - _Why:_ The crossed cells hold the recipient fixed while changing only the source of the first chunk, and actual-observation continuation avoids replay-prefix or stale-cache artifacts.
6. **Estimate the matched-state interaction** (`S6`)
   - Form a complete quartet for each $pair_{id}, policy_{id}, reset_{seed},$ and registered stratum only when all four eligible $Y_{r\leftarrow s}$ cells are present. Compute the two within-recipient own-source-minus-cross-source binary contrasts and average them to obtain that quartet's matched-state interaction $I_{MS}.$ Within each task-family, policy, and endpoint-equal baseline stratum, first average complete quartets over reset seeds for each geometry pair and then average geometry pairs with equal weight, preventing seed count from reweighting a pair. For paired uncertainty, enumerate the exact with-replacement bootstrap distribution over pair identifiers within the stratum while keeping every seed and all four cells of a sampled pair together; report the conventional two-sided 95% percentile interval because it exposes estimator uncertainty without assuming Gaussian binary contrasts. Report per-stratum point estimate, interval, numbers of registered pairs and complete quartets, and eligibility coverage defined as complete deterministic-passing quartets divided by all registered quartets, with excluded counts split by reason code. Do not pool strata into an unregistered overall effect.

*The matched-state interaction averages each recipient's own-source advantage, canceling a recipient geometry that is simply easier.*
$$ I_{\mathrm{MS}}=\tfrac{1}{2}\left[\left(Y_{A\leftarrow A}-Y_{A\leftarrow B}\right)+\left(Y_{B\leftarrow B}-Y_{B\leftarrow A}\right)\right] \tag{4} $$

   - _Why:_ The symmetric interaction cancels recipient difficulty and targets selective own-geometry compatibility rather than raw success or action difference.

### M2_validation
*Test the interaction against appearance-only controls, matched-state jitter, and deterministic-query failures.*

7. **Apply mechanism validity gates** (`S7`)
   - Run the S6 estimator unchanged on the appearance-only records and on copies of each functional checkpoint after applying the same registered state perturbation to A and B while preserving pair invariants. Store each perturbation as a typed record containing state-field path, coordinate frame, signed direction, magnitude, recipient-shared application rule, validity checks, and resulting checkpoint digests. The perturbation and two statistical gate predicates are not defined. 【author decision: preregister the jittered fields, coordinate frame, direction set, smallest nonzero magnitude, invariant checks, and the stratum-level uncertainty rules for systematically positive appearance effects and jitter sign reversal.】 Build a gate table per task-family, policy, and endpoint-equal stratum containing the functional, appearance, and jitter $I_{MS}$ estimates and intervals, determinism audit status, each registered predicate result, excluded-count breakdown, and final pass/fail value. Evaluate the existing disjunction exactly: return fail if the registered appearance predicate is true, the registered jitter-reversal predicate is true, or any required identical-render determinism audit fails; otherwise return pass, bounded to the eligible records represented in that table.
   - _Why:_ These gates distinguish functional geometry compatibility from texture preference, checkpoint brittleness, and hidden stochastic inference state.

It does not subsume the robot contribution on the available abstract: GISS-2x2 explicitly clones one fresh inference/history template, resets decode noise for both source queries, rejects nondeterministic identical-render repeats, discards every source-query cache before continuation, and restarts the recipient from its actual post-chunk observation. The collision therefore sharpens a necessary validity condition already present rather than establishing the same geometry-action assay.
